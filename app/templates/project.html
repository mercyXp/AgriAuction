In short

Farmers register produce lots. Buyers bid. The winning bid becomes a sale. Payments and collection follow. The whole flow sits on a normalised MySQL database with a working Flask application — including security, transactions, reports, views, procedures, indexes, backup and CRUD.

1. General instructions

Students work in groups of at least five. Each group is assigned one scenario and must design and implement its own database and application.

Incomplete work: a database without a working application, or an application that does not connect to the implemented database, is not accepted.

Approved DBMS

  • MySQL Workbench
  • Microsoft SQL Server

This group uses MySQL 8 with MySQL Workbench.

Allowed application tools

Python, Java, C++, PHP, JavaScript, HTML, CSS.

This group uses Python Flask, HTML, CSS, Bootstrap 5 and vanilla JavaScript.

  • The system must contain realistic sample data and demonstrate meaningful business operations — not only basic forms.
  • Submit a GitHub repository with a concise technical report, database scripts and application source code.
  • Each group must give a live class demonstration. Every student must participate and may be asked to explain or change any part of the database or application.
  • Deadline: 12 October 2026.

2. Group 2 scenario

AgriAuction Digital Produce Trading Platform

AgriAuction runs agricultural produce trading centres. Registered farmers bring crops such as maize, soya beans, groundnuts and beans. Produce is inspected, graded and registered as a produce lot. Registered buyers place bids. The successful bid becomes a sale. Payments and collection of the purchased produce are then recorded.

Current problems

The organisation currently uses several spreadsheets. That makes it hard to:

  • See the current status of a produce lot.
  • Identify the highest valid bid.
  • Prevent a lot from being sold twice.
  • Reconcile buyer payments with completed sales.
  • Analyse average prices by crop and grade.
  • Analyse volumes supplied by farmers.
  • Analyse purchasing activity by buyers.

3. What Group 2 must develop

A database and application to manage:

  • Farmers
  • Buyers
  • Produce types
  • Produce lots
  • Quality grades
  • Depots
  • Bids
  • Successful sales
  • Payments
  • Collections

Important business rules

Prevent bids on closed lots.
Prevent the same produce lot from being sold more than once.

4. Required application operations

Users should be able to:

  • Register farmers and buyers.
  • Create produce lots.
  • Enter bids.
  • Close an auction and identify or record the winning bid.
  • Process payments and record collection.

Required transaction

At least one multi-step operation must use transaction control. For Group 2 the natural example is closing an auction and creating the corresponding sale.

If processing is incomplete or something fails, the database must not leave inconsistent records (atomicity).

5. Compulsory requirements

These apply to all groups. Group 2 must implement every item below.

  1. Requirements analysis & business rules

    Identify main users, system requirements and important business rules. Separate rules enforced by the database from rules handled by the application.

  2. Conceptual database design

    Create an ERD showing entities, attributes, relationships, cardinalities and identifiers.

  3. Relational schema

    Convert the ERD into tables. Identify primary keys, foreign keys and constraints.

  4. Normalization

    Show 1NF, 2NF and 3NF. Explain the dependencies removed at each stage.

  5. Database implementation

    Implement the database in MySQL Workbench or SQL Server: tables, data types, primary keys, foreign keys and integrity constraints.

  6. Sample data

    Use realistic data. Major tables should normally have at least 10 meaningful records so queries, reports and the application can be demonstrated.

  7. SQL queries

    Demonstrate DDL, DML, SELECT, filtering, sorting, aggregate functions and GROUP BY.

  8. Joins & subqueries

    Demonstrate INNER JOIN, at least one other appropriate JOIN, and at least one meaningful subquery.

  9. Views

    Create at least two useful database views.

  10. Stored procedures

    Create at least two meaningful stored procedures relevant to AgriAuction.

  11. Transactions & ACID

    Implement at least one multi-step business operation with transaction control — for example close auction → determine winner → create sale. Be able to explain Atomicity, Consistency, Isolation and Durability.

  12. Indexing & query optimization

    Create appropriate indexes for frequently searched or joined data and explain why they were selected.

  13. Database security

    Implement database users/roles, different privileges, authentication, authorization and least privilege. Do not hard-code sensitive credentials in the application.

  14. Backup & recovery

    Create a database backup, demonstrate or document restoration, and explain what data could be lost under the backup strategy.

  15. Application development

    Develop a working application connected to the implemented database. It must not only display static or hard-coded information.

  16. CRUD

    Demonstrate Create, Read, Update and Delete while respecting business rules and user privileges.

  17. Business transaction

    Implement at least one scenario-specific process that affects multiple related records, with validation and transaction handling.

6. Minimum application functionality

The Group 2 application must include:

  • Login or appropriate user identification.
  • Data-entry forms for major entities.
  • Working CRUD operations.
  • Validation of important business rules.
  • Search and filter functionality.
  • At least two useful reports or management summaries.
  • At least one multi-table business transaction.
  • Clear error handling.
  • A direct connection to the database.

7. Live demonstration / oral defence

The lecturer may ask any group member to demonstrate or explain the system. Be prepared to:

  • Explain an entity, relationship, primary key or foreign key from the ERD.
  • Explain how a table was normalised and identify a functional dependency.
  • Write or modify an SQL query; run a JOIN, a subquery, a view and a stored procedure.
  • Perform CRUD through the application and verify the change in the database.
  • Explain the transaction and what happens if part of it fails.
  • Explain an index and why it was created.
  • Demonstrate database-user permissions.
  • Show the backup and explain restoration.
  • Explain where NoSQL could complement the relational database.
